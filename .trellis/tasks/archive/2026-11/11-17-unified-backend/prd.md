# 신청자·담당자 연결 (백엔드 통합)

Source: 팀장 요청 2026-11-17 — "두배적금 두 레포에 대해서, 신청자 화면에서 신청하면 운영자 DB에서 보일 수 있도록 이어 보기".

## Goal

두배적금 신청자 화면(`26-2-savings-applicant`의 프런트)에서 낸 신청이 담당자 화면(이 저장소의 프런트)과 이 저장소의 DB(`demo/demo.db`)에 바로 보이게 한다. 이 저장소의 백엔드 하나가 두 화면의 API를 모두 제공한다.

## Background

- 두 저장소의 백엔드는 분리 전 코드에서 갈라졌고 API 경로 42개와 DB 모델이 같다. 지금은 각자 자기 저장소의 `demo/demo.db`와 `demo/storage`를 써서 데이터가 이어지지 않는다.
- 신청자 프런트는 `/api/applications`·`/api/programs`만, 담당자 프런트는 `/api/officer`·`/api/files`만 부른다. 두 프런트 모두 개발 프록시 기본값이 `localhost:8000`이다.
- 분리 뒤 신청자 저장소는 신청자 응답 경계(내부 판정 숨김, 3단계 제출 확인)를, 이 저장소는 업로드 판정(화질 등급, 납부확인서 구조)을 바꿨다. 제품 코드에서 양쪽이 함께 바꾼 파일은 2개이고 자동 3방향 병합에 충돌이 없다.
- 근거와 파일 목록은 `research/findings.md`에 있다.

## Requirements

- **R1 합친 백엔드** — 이 저장소의 `demo/backend`가 신청자 저장소의 신청자 API 동작과 이 저장소의 판정 동작을 함께 가진다. 한쪽만 바꾼 파일은 바꾼 쪽 것을 쓰고, 양쪽이 바꾼 파일은 3방향 병합한다.
- **R2 신청자 응답 경계** — `/api/applications`·`/api/programs` 응답은 신청자 저장소의 계약(`applicant-submission.md`)과 같다. 서류 상태는 `UPLOADED`·`REUPLOAD_REQUIRED`뿐이고, 사유는 허용 목록 10개의 FAIL만 나간다. 점수, 자격 사유, 판독 신뢰도, 판정 기준 안내는 나가지 않는다.
- **R3 담당자 화면 불변** — `/api/officer`·`/api/files` 응답과 담당자 프런트 코드는 바뀌지 않는다.
- **R4 판정 불변** — 업로드 판정, 판독, 엔진(`engine`, `engine_v2`)은 이 저장소의 지금 동작 그대로다. 저장되는 판정과 `Review`는 신청자 응답 경계와 무관하게 온전히 남는다.
- **R5 시험 이전** — 신청자 저장소가 바꾼 시험과 시연 기대값을 가져오고, 양쪽이 바꾼 시험은 병합한다. 이 저장소가 분리 뒤 추가한 시험 가운데 신청자 API의 상태 값으로 내부 판정을 확인하던 단언은, 저장된 판정을 직접 읽도록 고친다. 바뀌는 시험과 기대값은 `changed-test-expectations.md`에 있는 것뿐이다.
- **R6 연결 실행** — 백엔드 하나에 프런트 둘을 붙여 실행하는 절차를 문서로 남긴다. 프런트 코드를 고치지 않고 실행할 수 있어야 한다.
- **R7 실제 화면 확인** — 합성 서류로 신청자 화면에서 제출한 건이 담당자 목록과 상세에 나타나고, 담당자가 내린 결정이 신청자 마이페이지에 보이는지 확인한다.
- **R8 규격과 문서** — `.trellis/spec`에 신청자 응답 경계 규격을 들이고 양쪽이 바꾼 규격을 병합한다. `README.md`, `docs/DEVELOPMENT.md`를 갱신한다.

## Acceptance Criteria

- **AC1 (R1, R4)** 병합 뒤 `demo/backend`의 제품 코드가 조사 기록 4절의 처리 표와 일치한다. `engine`, `engine_v2`, `demo/frontend` 변경 0.
- **AC2 (R2)** 신청자 저장소에서 가져온 신청자 경계 시험(`test_applicant_submission_policy.py`, `test_applicant_supplement_projection.py`, `test_applicant_failure_findings.py` 등)이 이 저장소에서 통과한다.
- **AC3 (R3)** 담당자 API 시험과 담당자 프런트 검사(`tsc`, `oxlint`, 빌드, `npm test`)가 변경 전과 같다.
- **AC4 (R5)** 엔진·백엔드·시나리오 시험의 실패 목록이, 같은 PC에서 잰 변경 전 두 저장소의 실패 목록으로 모두 설명된다. 새로 생긴 실패 0.
- **AC5 (R7)** 실제 화면에서 제출 → 담당자 목록·상세 → 담당자 결정 → 마이페이지 순서가 한 DB에서 이어진다.
- **AC6 (R6, R8)** 문서의 절차대로 실행하면 연결 구성이 뜨고, 규격과 문서가 합친 동작과 일치한다.

## Out of Scope

- 두 백엔드 사이의 데이터 전송, DB 파일 공유.
- 신청자 저장소의 백엔드·엔진·시험 변경. 신청자 저장소의 문서 안내는 별도 태스크다(D3).
- 프런트 코드 변경, 로그인과 권한.
- 두 저장소의 기존 `demo.db`·`storage` 데이터 옮기기(시연용 합성 자료다).
- `fcntl` 때문에 Windows에서 수집되지 않는 시험의 수정.

## Key Decisions

- **D1** 방식은 "백엔드 하나, DB 하나, 프런트 둘"이다(2026-11-17 팀장 결정). DB 공유와 전송 방식은 택하지 않았다.
- **D2** 합친 백엔드는 이 저장소(담당자 저장소)에 둔다(2026-11-17 팀장 결정). 판정 코드와 엔진이 이미 여기 있어서 가져올 것이 적다.
- **D3** 신청자 저장소의 백엔드 코드는 그대로 둔다. 신청자 저장소에는 연결 실행 안내를 문서에만 더한다(2026-11-17 팀장 결정). 그 문서 변경은 이 태스크가 끝난 뒤 신청자 저장소의 별도 태스크와 PR로 한다.
- **D4** 신청자에게 다시 올리라고 안내하는 사유의 허용 목록은 신청자 저장소의 10개 그대로다. 이 저장소가 분리 뒤 새로 만든 사유 코드 1개(납부확인서 쪽수 불확실)는 담당자 확인용이라 넣지 않는다. 이 태스크는 두 정책을 합치기만 하고 어느 쪽 정책도 바꾸지 않는다.
- **D5** 실제 화면 확인은 임시 DB를 쓰는 격리 서버에서 한다. 이 저장소의 시연용 `demo/demo.db`에는 시험 신청을 넣지 않는다.

## Risks

- 양쪽 변경이 동작으로 어긋날 수 있다. 저장소 밖 사본의 시험에서는 어긋난 곳이 없었다(`research/findings.md` 7절). 실제 적용 뒤 다시 확인하고, 정책 선택이 필요한 곳이 나오면 멈춰서 묻는다.
- 이 PC는 Windows라 일부 시험이 수집되지 않는다. 그 모듈은 이 PC에서 확인할 수 없다.
- 신청자 API 코드가 두 저장소에 있게 된다. 이후 신청자 API를 고치면 양쪽에 반영해야 한다.
