# 설계 — 2026-11-13 구현 승인

## 경계와 화면
이번 변경은 하나의 통합 태스크로 관리한다. 진입·목록·상세·시연 절차가 함께 검증되어야 하므로 따로 시작/완료하는 하위 태스크로 나누지 않는다.

- App.tsx에서 OfficerConsole만 마운트한다. 신청자/담당자 전환, 신청자 헤더, 사업 소개를 제거하고 문서 제목과 상단명을 두배적금 담당자용으로 바꾼다.
- 기본 경로는 /officer다. / 및 옛 /apply 경로, 타 사업·기준 관리 경로는 담당자 첫 화면으로 정규화한다. 새로고침·뒤로/앞으로 이동을 지원하며 다른 사업/역할을 URL에서 복구하지 않는다. 새 라우팅 패키지는 도입하지 않는다.
- hub/province 역할과 double_savings 사업을 고정한다. 첫 화면의 역할 전환·사업/판정 필터·정원·점수/순위 요약·일괄판정·기준 관리 진입은 제거하고 두 목록만 남긴다. 백엔드의 대응 기능은 보존한다.

## 서류 목록 모델
기존 GET /api/officer/applications?role=province&program=double_savings를 사용한다. ai_status는 신청 건의 통합 상태 필터이므로 두 서류 목록 분류에 쓰지 않는다.

1. 기존 API는 신청 건 페이지를 반환하고 page_size를 최대 200으로 제한한다. page_count의 나머지 페이지까지 조회한 후 서류를 펼쳐 분류한다. 현재 페이지를 전체 건수처럼 표시하지 않는다. 필요하면 각 서류 목록에 표시 개수/페이지 처리를 둔다.
2. 각 항목에 application_id, application_no, 이름, 서류명, document_id, slot_key, 원래 status를 보존한다. 같은 신청의 PASS 문서와 그 외 문서는 각 목록에 나뉘어 나타난다.
3. status === 'PASS'만 '적합 서류', 나머지 전부는 '확인 필요 서류'에 둔다. FAIL을 NEEDS_REVIEW로 바꾸거나 신청의 final_status를 덮어쓰지 않는다. 미배정 문서도 document_id로 구별한다.
4. 기존 API가 주는 미제출 항목(status/document_id가 null)도 확인 필요에 포함한다. 원본이 없는 항목에는 '미제출 — 원본 없음'을 보여주며 다른 문서를 대신 열지 않는다. 필수 여부·원래 상태를 보존하고 새로운 부적합 사유는 생성하지 않는다.
5. 빈 목록·로딩·실패를 구별한다. 프런트 목업은 ?mock=1 명시 모드로 유지하고 기본 API 오류나 빈 결과를 숨기지 않는다. 목업 생성·필터·상세에서도 취업지원 데이터/분기를 제거한다.

이는 현재 데모 규모의 최소 변경안이다. 대규모 운영을 위한 문서 전용 서버 페이지 API는 범위 밖이며 API 계약 변경 없이 시작한다.

## 원본·사유 2단 상세
기존 ReviewDetail과 DocumentViewer를 재사용하고 선택값을 application_id + document_id + slot_key로 전달한다. 기존 슬롯만으로 고르는 코드(ReviewDetail.tsx:90)는 미배정 페이지가 여러 장이면 잘못된 문서를 열 수 있어 ID 우선으로 바꾼다. URL에도 선택 문서를 기록한다.

왼쪽에는 선택 문서 원본을 인라인 표시한다. 오른쪽에는 해당 문서 findings의 code/message/how_to_fix 및 기존 필요 안내를 그대로 표시한다. 기존 신청 전체 이유를 남기면 '신청 전체 사유'로 구분해 선택 문서의 사유로 오해하지 않게 한다. 사유를 재계산·재작성·추가 설계하지 않는다. 취업지원 지급 내역·선착순·보완기간 전용 패널을 제거한다. 두배적금 기존 심사표/담당자 저장 동작은 상세에서 유지할 수 있으나 첫 화면에는 노출하지 않는다.

조회한 상세의 program_code도 확인하여 URL로 취업지원 신청 ID를 입력해도 관련 화면이 열리지 않게 한다. 목록에 없는/삭제된 문서 ID는 명시적인 없음 상태로 처리하고 첫 문서로 조용히 대체하지 않는다.

- 제거: src/pages/applicant 전체, 신청자만 사용하는 src/forms UI/모델, SignaturePad 및 신청자 전용 미리보기/메뉴 등(구현 시 import 그래프 확인 후 확정), CriteriaEditor의 제거된 진입에만 필요한 코드. api.ts의 신청자/취업지원 전용 프런트 호출·타입·표시 분기는 실제 참조 확인 후 정리한다.
- 유지: 신청·서식·업로드·판정·취업지원 백엔드 API, 모델, 저장 결과, engine/ 및 engine_v2/.
- 유지: src/assets/fonts의 TTF/WOFF2/OFL. backend/forms/render.py:40 및 P7/P14 시험이 사용한다. 신청자 UI와 함께 지우지 않는다.
- 유지: demo/fixtures/templates, form_coords, expected, 합성 샘플 생성기. 신청자·취업지원 백엔드 시험도 모두 유지한다.
- 보존 대상 코드에는 화면 제거를 이유로 동작 수정을 하지 않는다. 예상 밖 변경 필요 시 계획을 갱신해 다시 승인받는다.

## 시연 데이터 (새 도구 제안)
research/demo-data.md의 별도 seed_officer_demo 최소안을 승인 대상으로 제시한다. 기존 seed_application의 본인인증 불변 계약은 유지한다. 기존 신청·서류·판정은 건드리지 않고 새 합성 신청만 추가한다. API를 통한 정상 제출과 확인 필요 제출의 두 시연 건이면 양쪽 목록과 상세를 재현할 수 있다. 확정 FAIL 제출을 통과시키는 우회는 추가하지 않는다.

## 문서와 호환성
README는 담당자 목적·네 저장소 관계·설치·지정 실행 명령·시연 주입/정리만 중심으로 재작성한다. 개발/데모 안내는 저장소 주소, 첫 진입/기능, 시연 데이터, 검증 수치 등 바뀐 사실만 갱신한다. 과거 저장소 브랜치 표는 이 저장소 현황인 것처럼 안내하지 않는다. 대시보드와 과거 문서 전체 정비는 제외한다.

## 되돌리기
DB 스키마 변경과 기존 판정 변경이 없으므로 화면/문서 변경을 되돌리면 기존 UI로 복구된다. 새 시드가 승인되어 구현되면 도구가 표시한 합성 신청/파일만 정리한다. 전체 DB reset이나 시나리오 --live는 사용하지 않는다.

## 구현 중 확인한 경계
- 일반 생성 API의 접수번호는 전체 신청 수+1이라 삭제로 번호에 간격이 생기면 충돌할 수 있다. 새 시드에 한해서 전용 UUID 접수번호와 기존 최신 기준 버전으로 새 Application을 할당하고, 그 다음 서식·업로드·제출 핸들러는 그대로 재사용한다. 기존 API/모델/판정은 수정하지 않는다.
- 기존 합성 시험이 일반번호로 남긴 forms_exports 파일은 열거나 삭제하지 않는다. 시드 전용 번호로 파일 namespace를 분리한다.
- 신청자 UI 제거 후에도 같은 신청의 문서 탭 이동 때 담당자 메모를 유지한다. 원본 PDF 한 쪽 로딩 완료의 렌더 트리거를 보강한다.
