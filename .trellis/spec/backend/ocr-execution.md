# OCR execution model (11-28 이벤트 루프 차단 해결)

업로드 서류의 자동 판독을 **어디서, 몇 건씩** 돌리는지에 대한 규칙이다. 두 백엔드(savings-officer·youth)에서 같다:
`demo/backend/ocr_gate.py`는 공통 OCR 일치 검사(`common-ocr-parity.md`) 대상이다. 판독 내용·판정 규칙은 바꾸지 않는다.

## 문제 (main 9d6072d / 8b56357에서 재현)

업로드 핸들러 `upload_document`는 `async def`이고 판독(`assess_upload` → `read_document`)을 그 안에서 동기로 불렀다.
판독이 이벤트 루프 스레드에서 돌았으므로:

- 한 건을 읽는 동안 그 프로세스의 **모든 요청이 멈췄다.** `/api/health` 지연 = 판독 시간(실측: 3쪽 2.2초, 10쪽 11초, 20쪽
  21초, 30쪽 잡음 스캔 74초 — 기기 발열 상태에 따라 20쪽 15~22초, 30쪽 57~74초). 동시 업로드가 쌓이면 합계만큼(20쪽 8건
  184초) 멈췄다.
- 루프가 멈춘 동안 DB 쓰기 대기 시한(5초)이 지나가 **의도하지 않은 503**이 났다(3쪽 8건 중 2건, 10쪽 4건 중 1건·8건 중 4건,
  20쪽 8건 중 1건). `async_session_transaction`의 시한은 벽시계 기준인데, 쓰기 예약을 쥔 요청도 같이 멈춰 있었기 때문이다.

## 실행 모델

| 항목 | 값 | 근거 |
|---|---|---|
| 판독 위치 | 전용 작업 스레드 `ocr-read` 1개 (이벤트 루프·요청 스레드풀 밖) | 루프를 막지 않는다 |
| 문서 동시 판독 | **프로세스당 1건**, 설정 불가 (`MAX_CONCURRENT_READS`) | 아래 "왜 1건인가" |
| 대기 상한 | 8건 (`OCR_MAX_WAITING_READS`) | 넘으면 저장 전에 503 + `Retry-After` |
| 대기 시한 | 90초 (`OCR_MAX_QUEUE_WAIT_SECONDS`) | 신청 화면의 업로드 대기 120초. 시한을 넘긴 대기 건은 읽지 않고 503 |
| 판독 시간 한도 | 쪽 판독 한 번에 180초 (`limits.MAX_OCR_SECONDS`, 쪽 경계에서 확인) | `ocr-resource-limits.md`. 한 건이 1차 판독 뒤 대체 판독을 하면 각각 따로 잰다(최악 2배). 쪽 그림을 만드는 전처리와 한 쪽 안의 렌더링은 이 시간에 묶이지 않는다 |

`ocr_gate.reserve()`로 자리를 잡고 `ticket.run(function, ...)`으로 판독 한 번을 작업 스레드에 맡긴다. 핸들러는 결과를
`await`하고, 그동안 이벤트 루프는 다른 요청을 처리한다.

작업 스레드는 프로세스가 사는 동안 하나를 그대로 쓴다(다시 만들지 않는다 — 새로 만들면 앞 판독이 끝나기 전에 다음 판독이
시작될 수 있다). 판독은 DB 쓰기 예약 밖에서만 맡긴다: 예약 안에서 부르면 `RuntimeError`다(`upload_document`의 확인).

**자동 판독이 없는 칸은 차례를 타지 않는다 (youth)**: 결제영수증 원본(수동 검토)과 담당자 정의 서류(`DocType.UNKNOWN`)는
판독기를 부르지 않는다(`upload_assessment.reads_document`). 이런 업로드는 자리를 잡지 않고 요청 스레드풀에서 파일 확인만
한다 — 다른 신청자의 판독이 길어도, 대기열이 가득해도 바로 저장된다. 이 경로에는 호출되면 오류를 내는 판독기를 넘겨,
조건이 어긋나 판독이 대기열 밖에서 도는 일이 없게 한다. 두배적금에는 이런 칸이 없다.

### 왜 1건인가 (처리량은 늘지 않는다)

- 문서 한 건이 이미 쪽 단위로 병렬이다: 쪽 작업 최대 4개 × ONNX 스레드 2개 = 8코어. 판독 중 서버 CPU는 3쪽 약 460~490%,
  10쪽 약 610~630%, 20쪽 약 690~700%다(8코어 = 800%, 검증 기록의 부하 측정). 문서 두 건을 겹치면 스레드가 코어의 두 배가 된다.
- 메모리는 판독 중인 쪽 세션 수에 비례한다(세션당 약 0.34GB, `ocr-resource-limits.md`의 11-27 측정). 두 건이 같은 세션을
  함께 쓰면 그만큼 겹친다.
- PyMuPDF는 여러 스레드에서 동시에 쓰는 것을 지원하지 않는다(단일 스레드 초기화). 판독 스레드를 하나로 두면 판독끼리는
  겹치지 않는다.
- 따라서 **이 변경은 처리량을 늘리지 않는다.** 판독은 전과 같이 한 건씩이고 한 건의 판독 시간도 같다. 달라지는 것은
  판독 중에도 다른 요청이 응답한다는 점과, 루프 정지 때문에 나던 503이 없어진다는 점이다.

### 비교한 대안

| 대안 | 판단 |
|---|---|
| 그대로(루프에서 판독) | 문제 그대로 |
| 요청 스레드풀(`run_in_threadpool`, 기본 40스레드)에 맡김 | 문서 동시 판독이 제한 없이 생긴다(CPU·메모리 중첩, PyMuPDF 동시 사용). 기각 |
| 전용 스레드 + 세마포어 N>1 | 위 "왜 1건인가"와 같은 이유로 N=1 |
| 별도 프로세스(ProcessPool) | 실행 중인 판독을 실제로 중단할 수 있고 GIL 영향이 없다. 대신 프로세스마다 모델(서버 대기 메모리 약 0.3GB)을 따로 올리고 결과를 직렬화해야 하며 구조 변경이 크다. 이번 범위 밖(남은 제약 참고) |

## 취소·시한·과부하

- **요청 취소**: 아직 시작하지 않은 판독은 실행하지 않고 자리를 바로 놓는다. **이미 시작한 판독은 멈출 수 없다**(파이썬
  스레드는 밖에서 중단되지 않는다). 그 판독이 실제로 끝날 때까지 자리를 차지한 것으로 세고, 다음 판독은 그 뒤에 돈다.
  결과는 버리고 행을 저장하지 않으며, 업로드 파일은 **판독이 끝난 뒤에** 지운다(`ticket.after_read`).
- **브라우저가 연결을 끊은 경우**: uvicorn은 연결이 끊겨도 핸들러를 취소하지 않는다(전과 같음). 업로드는 끝까지 처리되어
  저장되고, 신청자가 화면을 다시 열면 보인다. 같은 칸에 다시 올리면 앞 요청이 끝난 뒤 처리되어 마지막 파일로 교체된다.
- **타임아웃은 중단이 아니다**: 대기 시한(90초)은 **시작하지 않은** 판독에만 적용한다. 시작한 판독을 밖에서 시간으로
  끊는 기능은 없다 — 판독이 스스로 쪽 사이에서 확인하는 한도(쪽 판독 한 번에 180초)만 있다.
- **과부하 503**: 대기열이 가득하거나 대기 시한을 넘기면 `503 {"detail": "지금 서류 자동 확인 요청이 많습니다. 잠시 후 다시
  올려 주세요."}` + `Retry-After: 10`. 거절된 업로드는 저장소에도 DB에도 흔적이 없다. 신청 화면은 503에 고정 문구를
  보여 주고 자동으로 다시 보내지 않는다(신청자가 다시 올린다).
- **서버 종료**: 정상 종료(SIGTERM)에서 uvicorn은 진행 중인 요청이 모두 끝나기를 기다린 뒤 수명 종료 훅을 부른다. 그래서
  판독 중인 업로드도, 차례를 기다리던 업로드도 끝까지 처리되어 응답한 다음 서버가 내려간다(실측: 20쪽 판독 중 SIGTERM →
  업로드 200, 종료까지 9.6초). 종료 대기 시간을 제한해 띄운 서버(`--timeout-graceful-shutdown`)는 그 시간이 지나면 요청을
  취소한다: 대기 중인 판독은 실행하지 않고, 실행 중인 판독은 멈출 수 없어 끝까지 돈 뒤 프로세스가 내려간다. 수명 종료 훅의
  `ocr_gate.shutdown()`은 그때까지 남은 대기 건을 버리는 정리 단계다(대기하던 요청이 살아 있으면 503). 강제 종료(SIGKILL)는
  판독 중이던 업로드의 파일만 저장소에 남고 행은 없다(저장은 판독 뒤 한 트랜잭션, 실측).
- **상태 확인**: `/api/health`는 프로세스가 응답하는지만 본다. 판독 스레드가 한 건에 오래 묶여 있어도 200이다. 대기열이
  가득해 업로드를 거절할 때 진행 중인 판독이 몇 초째인지 경고 로그에 남긴다.

## 보존하는 것 (회귀 금지)

- 판독·판정 함수와 입력은 전과 같다(`assess_upload` 그대로). 실제 ONNX 안전 말뭉치 대조 결과는 검증 기록에 있다.
- 신청 쓰기 잠금(flock)은 요청이 판독을 기다리는 동안에도 쥐고 있다 → 같은 신청의 다른 쓰기(제출·교체·삭제)는 전처럼
  차례를 기다린다. 판독 뒤 저장 전에 초안 상태와 신청 입력값을 다시 읽어 바뀌었으면 409(전과 같은 검사).
- 판독은 DB 쓰기 예약(`BEGIN IMMEDIATE`) **밖**에서 한다. 판독 스레드는 요청의 contextvars를 복사해 쓰므로 잠금 표시
  (`_held`)가 이어지고, 쓰기 예약 연결(`_session_bind`)은 그 시점에 없다.
- 제출 후 문서 불변, 담당자 Review CAS, 인증·권한 미들웨어는 손대지 않았다.

## 프로세스별 한도와 여러 프로세스

- 모든 수치는 **프로세스 하나** 기준이다. `uvicorn --workers N`이면 프로세스마다 판독 1건·대기 8건이고 모델도 프로세스마다
  올린다(최대 메모리 ≈ N × 한 프로세스). 전체 동시 판독 수는 N이 된다.
- 여러 프로세스·여러 서버에 걸친 전체 상한은 이 모듈이 보장하지 않는다. 필요하면 앞단(리버스 프록시)의 동시 연결
  제한이나 별도 작업 큐가 있어야 한다.
- 신청 쓰기 잠금(flock)과 SQLite 쓰기 예약은 같은 호스트의 프로세스 사이에서 전처럼 동작한다.

## 남은 제약

- 판독 스레드가 GIL을 쥔 채 도는 C 호출(PyMuPDF) 동안에는 이벤트 루프도 그만큼 기다린다. 판독 중 `/api/health` 지연은
  0이 아니다. 가장 길던 구간은 MuPDF의 PNG 인코딩이었다(잡음 있는 300dpi 스캔 한 쪽 약 1.1초를 쪽마다 연달아). 판독만
  스레드로 옮긴 단계에서는 30쪽 잡음 스캔을 읽는 동안 `/api/health` p95 3.3초, 최대 19.7초가 남았다 — 판독 스레드가
  연달아 GIL을 쥐는 사이 이벤트 루프가 다음 업로드의 본문 처리까지 밀린 것으로 본다. OCR 입력 PNG를 GIL을 놓는 OpenCV
  인코더로 만들도록 바꾼 뒤(`engine_v2.pipeline.preprocess.encode_png`, 화소는 같음) 같은 단계의 최대 지연은 0.2초 안쪽이다.
  남은 GIL 구간은 쪽 렌더링(300dpi A4 한 쪽 약 0.05초)과 그림 정보 읽기(약 0.03초)다(실측).
- **한 쪽의 렌더링이 오래 걸리는 문서는 그 시간만큼 프로세스를 멈춘다.** 가는 선 6만 개를 그린 합성 쪽은 300dpi 렌더링
  한 번(C 호출 하나)이 26초다. 호출 중에는 끊을 수 없고 시간 한도(180초)는 쪽 사이에서만 확인한다. 수정 전(28초)과 같은
  수준이며, 없애려면 판독을 별도 프로세스로 옮겨야 한다. 담당자 화면의 원본 미리보기 렌더링도 같은 성질이다.
- PyMuPDF는 단일 스레드 모드로 초기화되고 바인딩이 GIL을 놓지 않아서, 판독 스레드와 다른 요청(서식 미리보기 렌더링,
  youth 통장 사본 확인 등)의 PyMuPDF 호출이 한 번에 하나씩만 돈다. 이 안전성은 GIL에 기대고 있다 — GIL 없는 파이썬
  빌드나 GIL을 놓는 PyMuPDF로 바꾸면 판독과 다른 PyMuPDF 사용 사이에 잠금이 필요하다.
- 업로드 본문을 저장소로 옮겨 적는 동기 복사(두배적금 `_place_upload`)는 이벤트 루프에서 돈다(초안 확인과 저장 사이에
  다른 요청이 끼지 않게 하려는 기존 설계). 큰 파일에서는 그만큼 루프가 기다린다(따로 재지 않았다).
- 같은 신청자의 다음 업로드는 앞 판독이 끝날 때까지 기다린다(잠금). 다른 신청자의 글자층 PDF(OCR 불필요)도 판독
  차례를 기다린다 — 읽기 전에는 OCR이 필요한지 알 수 없다.
- 판독을 기다리는 요청은 연결 하나와 저장소의 업로드 파일 하나를 쥔다(최대 9건).
- 서명 스캔 처리(`forms.upload_signature_scan`)는 요청 스레드풀로 옮겼다(최대 2천만 화소, 실측 0.11~0.33초).
