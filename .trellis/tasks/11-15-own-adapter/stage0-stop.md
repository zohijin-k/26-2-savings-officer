# 0단계 중단 보고

조건 반영: 고정 오통과 상한 대신 새 0단계 기준값을 사용한다. 엔진별 × 종류별 증가 시 중단, own 0/235 유지, 참조 전후 완전 동일, PR #7 재현 확인 후 1단계 진입을 요구한다. 진단은 baseline의 실제 추출 함수를 그대로 사용하며 legacy 50쪽·정부형 20쪽을 서식별로 집계한다. 이 조건을 prd.md와 implement.md에 반영했다. 1단계 완료 보고가 생성되면 그 첫머리에도 같은 요지를 적는다.

격리 작업공간은 main의 추적 파일만으로 만들었다. 원본 서류·그 결과 폴더·기존 업로드·DB는 읽지 않았다. 설치 의존성/모델/글꼴 경로에 한정해 링크했고, 새 격리 공간에서 기존 회귀 시험만 실행했다. 별도 합성 글꼴 디렉터리는 없었지만 엔진 회귀의 건너뜀 수는 기준의 3과 같았다.

## 중단 원인과 근거

- 시작 시 가용 공간은 약 2.5GB였다. engine 완료 후 backend 실행 중 약 52% 진행에서 0.3GB를 관측해 사용자에게 중단을 알렸다.
- 중단 신호를 보내려던 시점에는 프로세스가 이미 exit 120으로 끝났다. 신호 도구는 sandbox의 프로세스 조회 서비스 부재로 실패했으며, 실제 종료는 신호로 인한 정상 중단이 아니다.
- backend 로그에서 ENOSPC(저장 공간 부족)를 2회 확인했다. 마지막 기록 진행률은 89%이며, 여러 모듈의 F/E 표시는 있지만 pytest 최종 집계가 없으므로 완료된 통과/실패 수를 확정하지 않는다.
- ENOSPC는 확인된 환경 오류다. 각 실패 사례의 개별 원인을 모두 디스크 부족으로 확정하지 않으며, 실패 상세가 정상 출력되지 않아 추가 원인은 미확정이다.
- 기존 시험/기대값/운영 코드는 변경하지 않았다. 재실행으로 실패를 덮지 않고 해당 지점에서 후속 작업을 중단했다.

가용 공간은 관측 시점마다 달라졌으며 전체 변화를 이번 정리에만 귀속하지 않는다. 기존 사용자 파일이나 다른 작업의 디렉터리는 삭제하지 않았다.

## 변경과 다음 단계

바뀐 것은 이 Trellis 작업의 계획·문맥·기록 파일뿐이다. 진단 도구·운영 코드·기존 시험 변경, 스테이징, 커밋, push는 없다. 1단계 진입 조건을 충족하지 못했으므로 경로 비교·합성 진단·원인 가설·수정안·실서류 실행 명령을 완료했다고 보고하지 않는다.

현재 작업은 in_progress 상태에서 0단계 중단 사유를 기록했다. 재실행 승인을 받으면 보존된 로그를 바탕으로 공간 상태를 확인하고 같은 backend 묶음부터 재검증한다. 임시 파일 누적 방지 조치가 필요하면 시험 코드/기대값을 건드리지 않는 실행 환경 방식을 먼저 설명한다. 1단계가 완료되지 않아 이번에는 커밋 승인을 요청하지 않는다.
