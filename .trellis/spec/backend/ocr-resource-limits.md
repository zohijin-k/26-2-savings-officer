# OCR resource limits (11-27 CPU·메모리 보호)

자체 OCR(own, PP-OCRv5 ONNX CPU) 판독이 쓰는 CPU 시간과 메모리를 묶는 규칙이다. 공통 OCR 기술이므로 두 저장소
(savings-officer·youth)에서 같다(`common-ocr-parity.md`). 사업별 판정 규칙(Document AI)은 바꾸지 않는다.

**원칙: 자원 보호는 판독을 생략하는 방식으로 하지 않는다.** 한도 안의 문서는 전과 똑같이 모든 쪽을 읽고(같은 OCR 입력,
같은 판정), 한도를 넘는 문서는 **한 쪽도 판정에 쓰지 않고** 문서 전체를 담당자 확인으로 보낸다. 일부 쪽만 읽은
결과로 PASS나 FAIL을 내지 않는다.

## 측정으로 확인한 원인 (main 08bc4f4 / ec00da1, 8코어 M2 16GB, 합성 가상인 문서)

글자층 1쪽 + 스캔 19쪽 혼합 초본(300dpi 렌더링 20쪽)이 14~17초, 최대 1.8~2.9GB(실행마다 다름, 새 프로세스 5회 중앙값
2.55GB)를 썼다. 분해하면:

| 원인 | 크기 | 근거 |
|---|---|---|
| 동시 쪽 세션(det+rec) 4개의 추론 메모리 | 작업 1개 0.9GB → 2개 1.2GB → 3개 1.6GB → 4개 1.9GB (작업당 약 340MB) | 작업 수만 바꾼 반복 측정(판독 결과 동일). 가장 큰 몫이며 쪽 수와 무관 |
| 모든 쪽을 먼저 렌더링 + MuPDF 전역 캐시 | 20쪽 +425MB (OCR을 시작하기 전), 문서 최대 −0.3GB | 렌더링만 따로 측정: PNG 합계는 4MB뿐이고 나머지는 MuPDF가 쪽마다 디코딩한 그림을 놓지 않은 것(쪽마다 비우면 +104MB). 쪽 단위로 바꾸면 20쪽 중앙값 2.55 → 2.25GB(렌더링), 2.62 → 2.27GB(본문 그림) |
| onnxruntime CPU arena | 20쪽 렌더링 +0.24GB(2.25 → 2.01GB), 장시간 프로세스 +0.24GB(2.29 → 2.05GB) | arena 켬/끔 교차 반복. 실행마다 크기가 달라지고(1.97~2.55GB) 판독 뒤에도 쥐고 있음. 본문 그림 20쪽은 차이 없음 |
| 쪽 PNG 보관 | 깨끗한 합성본 0.2MB/쪽, 잡음 있는 스캔 10~20MB/쪽 | 판독이 끝날 때까지 쪽 목록이 전부 들고 있었음 |
| 서버 대기 메모리 | 300MB (세션 5개를 미리 불러옴) | `preload_own` 뒤. 바꾸지 않음 |

시간은 쪽 수에 비례한다: 깨끗한 합성 300dpi 쪽 0.7초, 잡음 있는 스캔 2.2초(쪽 그림 PNG 재인코딩이 한 줄로 돈다).
상한이 없어서 생기는 문제도 확인했다:

- 20KB짜리 PDF의 1.44억 화소 1비트 그림: 본문 그림을 찾는 `get_image_info(xrefs=True)`가 쪽의 그림을 전부 펼친다(+127MB, 0.7초).
- 쪽 크기 상한 없음: 5000×7000pt 쪽을 300dpi로 렌더링하면 6억 화소(쪽당 1.8GB).
- 쪽 수 상한 없음: 판독 시간이 쪽 수만큼 늘고, 업로드 판독은 서버 이벤트 루프에서 돌므로 그동안 그 서버의 다른 요청이 기다린다.
- 내용이 복잡한 쪽: 가는 선 6만 개를 그린 쪽 하나가 검출 상자 상한(쪽당 2,000개)까지 인식해 33초.
- 업로드 본문을 `await file.read()`로 한꺼번에 메모리에 올림(크기 제한 없음).
- PIL이 열기를 거부하는 초대형 사진(약 1.8억 화소 초과)은 `read_document` 밖으로 예외가 나가 HTTP 500.

## 바뀐 것

### 쪽 단위로 만들고 놓기 (공통)

- `localocr.render_pages(path)`는 컨텍스트 관리자다. `(쪽 목록, 쪽 그림 함수 목록)`을 내주고, 쪽 그림(300dpi PNG)은 그 쪽을
  읽을 차례에 함수가 만든다. 쪽 목록(`PageImage`)은 그림을 보관하지 않는다(`png=None`, `pixel_size`는 만들 때 채움).
- `engine_v2.pipeline.ocr.run_ocr_pages(engine, images, run)`의 `images` 항목은 `(png, size)` 또는 그것을 만드는 인자 없는
  함수다. 함수는 **호출하는 쪽의 스레드에서만** 부른다(PDF 라이브러리는 스레드 안전하지 않다). 동시 판독은
  `작업 수 × PAGE_LOOKAHEAD(2)`쪽까지만 앞서 만들어 맡기고, 앞 쪽 결과를 받아 가면 다음 쪽을 맡긴다. 쪽 순서·쪽별 결과는 같다.
- `limits.release_page_cache()`: 쪽 그림을 하나 만들 때마다 MuPDF 전역 캐시를 비운다(렌더링·본문 그림 꺼내기 모두).
- `own.CPU_MEM_ARENA = False`: 세션이 CPU arena를 쓰지 않는다. 판독 결과(상자·글자·신뢰도)는 같다. 3쪽 이상은 시간이 같고
  1쪽 문서는 0.02~0.03초(2~3%) 느리다(0.93 → 0.96초). 1쪽 문서와 본문 그림을 그대로 읽는 3쪽 스캔의 첫 판독 최대는 약 0.1GB
  높아진다(0.68 → 0.79GB, 1.45 → 1.55GB; 프로세스 최대보다는 낮다).
- `preprocess()`는 문서를 `with`로 열고 닫는다(전에는 닫지 않았다). 본문 그림을 그대로 읽는 경로는 지금도 모든 쪽의 PNG를
  먼저 만든다(도구·시험이 `PageImage.png`를 직접 쓴다). 그 보관량은 아래 문서 화소 합 한도로 묶인다.
- 업로드 API(`api/documents.py`, 사업별 파일): 본문을 1MB씩 받아 적는다(전에는 `await file.read()`로 전체를 메모리에).
  업로드 크기 계약은 그대로다(프런트는 20MB부터 '시간이 더 걸릴 수 있습니다'만 알리고 크기로 막지 않는다).
  officer는 본문을 신청 저장소 **밖** 임시 파일에 받고(`_receive_upload`), 초안 상태를 다시 확인한 뒤 저장 위치로 옮긴다
  (`_place_upload`) — 본문을 기다리는 동안 제출된 신청의 저장소에 아무것도 만들지 않는 기존 불변식
  (`test_status_is_rechecked_after_awaited_upload_read`)을 지킨다. youth는 기존 순서대로 저장 위치에 바로 적는다(`_store_upload`).

### 작업량 한도 (`engine_v2/pipeline/limits.py`, 공통)

| 한도 | 값 | 세는 것 | 근거 |
|---|---|---|---|
| `MAX_OCR_PAGES` | 30쪽 | OCR로 읽는 쪽(글자층으로 읽는 쪽 제외; 렌더링 대체 판독은 모든 쪽) | 쪽당 0.7~2.2초 → 30쪽 21~65초. 한 건이 서버를 붙잡는 시간을 약 1분으로 |
| `MAX_PAGE_PIXELS` | 6,000만 화소 | OCR 입력 그림 한 장, OCR할 쪽에 들어 있는 모든 그림, 공유 그림 확인용 72dpi 렌더 | A4 600dpi(3,480만)·5,000만 화소급 사진(8192×6144)까지. 쪽당 디코딩 그림 = 화소×3바이트(180MB) |
| `MAX_DOCUMENT_PIXELS` | 2.7억 화소 | 문서 한 건의 OCR 입력 화소 합 | 300dpi A4 30쪽 분량. 600dpi A4 7쪽, 5,000만 화소급 사진 5장 |
| `MAX_OCR_SECONDS` | 180초 | 쪽 판독 한 번(`run_ocr_pages`)의 경과 시간, 쪽 사이에서만 확인 | 잡음 스캔 30쪽 약 65초의 2.7배. 복잡한 쪽(33초/쪽)의 안전망 |

- 화소·쪽 수는 **그림을 펼치기 전에** 확인한다(쪽 크기, 그림 머리 정보만 읽음). `preprocess`는 먼저 문서 전체를 어림해
  (`_check_workload_before_decoding`) 31쪽 스캔이 30쪽을 디코딩한 뒤에야 거절되는 일이 없게 하고, 쪽을 처리하면서
  (`OcrWorkload.add`·`check_page_images`) 정확히 한 번 더 센다.
- 시간 한도는 `run_ocr_pages` 한 번 단위다. 1차 판독 뒤 300dpi 대체 판독이 이어지면 각각 따로 잰다(최악 2배).
  읽는 중인 쪽은 중단하지 않는다.
- 시간 한도는 서버 속도에 따라 달라지는 안전망이다. 정상 문서가 넘지 않게 넉넉히 잡았고, 넘으면 부적합이 아니라 담당자 확인이다.
- 본문 그림 찾기(`get_image_info(xrefs=True)`)는 쪽에 그리지 않은 자원 목록의 그림까지 펼치므로, 그 앞에서는 자원 목록의
  그림 크기도 확인한다(`check_page_images(page, resources=True)`). 사전 어림은 쪽 처리와 같은 기준(자원 목록에 있는
  쪽 덮는 그림의 화소, 인라인 그림뿐이면 300dpi 렌더 화소)으로 세어, 쪽 처리가 받아들일 문서를 미리 거절하지 않는다.
- 값은 합성 문서와 이 측정 기기 기준이다. 실제 서식의 쪽 수 분포를 재면 다시 정한다(낮출 때는 담당자 확인이 늘어난다).

### 한도를 넘었을 때 (실패 처리 정책)

`OcrWorkloadExceeded(code)`가 난다. **`ValueError`가 아니다** — 쪽 오류로 삼켜지거나(`engine._load_pages`) '파일을 열 수 없음'
(부적합)·다음 판독 계층(첫 쪽 글자층만 읽는 Tier2)으로 이어지면 안 되기 때문이다.

| 경로 | 결과 | 사유(`fallback_reason`, 담당자 화면 전용) |
|---|---|---|
| 글자층 초본에 그림 쪽이 섞인 문서 (`_read_raster_abstract`) | `_abstract_review_result`: 종류 초본, 신뢰도 0, 엔진 `none` | `RENDER_RETRY_FAILED:TEXT_RASTER_CONTENT:RESOURCE_LIMIT_<code>` |
| 그 밖 (`LocalOcr.read`) | 자동 판독 실패와 같은 모양: 종류 미판별, 신뢰도 0, 계층·엔진 `none` | `RESOURCE_LIMIT:<code>` |
| `engine_v2.engine.run` (도구) | `NEEDS_REVIEW`, 규칙 `ocr.workload` | — |

- `fields["판독실패"]`에 한글 사유(`localocr.workload_message`)를 남긴다. 담당자 화면은 판독값과 대체 사유를 그대로 보여 준다.
- 판정은 기존 규칙 그대로 **확인필요**다(종류 미판별 → `UNKNOWN_DOCUMENT_TYPE`, 초본 신뢰도 0 → `LOW_OCR_CONFIDENCE`,
  youth 영수증 → `RECEIPT_OCR_UNAVAILABLE`). PASS 없음, 읽지 않은 내용에 근거한 FAIL 없음.
- 신청자 화면: 두배적금은 중립 `UPLOADED`("업로드됨"), youth는 `NEEDS_REVIEW`("담당자 확인이 필요한 서류입니다"). 새 상태·코드는 없다.
- 파일 사실에 근거한 기존 확정 FAIL(암호·열 수 없는 파일, 사업별 화질 정책의 객관적 해상도 기준)은 그대로다.
- **예외 — `IMAGE_RESOLUTION_TOO_LOW`**: 이 FAIL은 '작은 그림(짧은 변 600px·긴 변 800px 미만) **그리고 읽지 못함**'이다. 한도로
  읽지 않은 문서는 '읽지 못함'이 아니므로 적용하지 않는다(`limits.not_read_by_limit(fallback_reason)` →
  `file_evidence.resolution_defect`가 건너뜀). 독립 검토에서 이 경로의 근거 없는 FAIL이 확인돼 막았다.
- 1차 판독(본문 그림)으로 모든 쪽을 읽었으나 서식을 못 찾아 시도하는 300dpi 대체 판독이 한도를 넘으면, 대체 판독만
  건너뛴다(`_from_ocr_pages`). 모든 쪽을 읽은 1차 결과이므로 '읽지 않음'으로 표시하지 않고 전과 같이 종류 미판별 확인필요다.
- 재시도: 신청자가 쪽 수·해상도를 줄여 다시 올리면 자동 판독된다. 서버가 자동으로 다시 읽지는 않는다.

## 보존하는 것 (회귀 금지)

- 한도 안 문서의 OCR 입력·판독 결과·판정은 전과 같다(실제 ONNX로 안전 말뭉치 before/after 대조).
- 혼합 PDF 전체 판독(`raster_content_pages` → 모든 쪽 렌더 OCR), `SCAN_ABSTRACT_REVIEW_GUARD`, FixtureOcr 기본 꺼짐,
  읽지 않은 쪽의 PASS 차단, 확정 FAIL, 사업별 Document AI, youth 영수증 수동 검토, API·권한·CAS 계약.
- 한도·시간 초과가 Tier2(PdfText, 첫 쪽 글자층)로 넘어가지 않는다 — `LocalOcr.read`가 `None`이 아닌 결과를 돌려준다.

## 동시성 (11-28 갱신)

- 판독은 이벤트 루프가 아니라 전용 작업 스레드에서 돈다(`ocr-execution.md`, `demo/backend/ocr_gate.py`). **서버 프로세스 하나는
  문서를 한 건씩 읽는다**는 점은 그대로다: 동시 업로드는 차례로 처리되고, 프로세스 최대 메모리는 한 건을 읽을 때와 같다.
  달라진 것은 판독 중에도 `/api/health`를 포함한 다른 요청이 응답한다는 점과 대기 상한(8건)·대기 시한(90초)이다.
- 문서 한 건 안에서는 쪽을 최대 4개(`OWN_OCR_PAGE_WORKERS`) 동시에 읽는다. 세션은 프로세스 안에서 재사용한다(문서마다 새로 만들지 않음).
- uvicorn 작업 프로세스를 여러 개 띄우면 메모리는 프로세스 수만큼 든다. 프로세스 하나의 최대: 문서 18건을 이어 읽을 때
  1.95~2.09GB(전 2.30~2.66GB), 한도 안에서 가장 큰 문서(600dpi 잡음 스캔 7쪽) 2.5GB(전 2.9GB).
- 메모리를 더 줄여야 하는 서버: `OWN_OCR_PAGE_WORKERS=2` → 20쪽 최대 약 1.2GB, 시간 +17%(작업 3개 1.6GB·+6%, 1개 0.9GB·+86%).
  변수를 설정하면 스레드가 고정값이 된다(`common-ocr-parity.md` 스레드 메모). 기본값(4)은 속도 조정 결과라 바꾸지 않았다.

## 남은 위험

- 본문 그림을 그대로 읽는 경로(`preprocess`)는 여전히 모든 쪽의 PNG를 먼저 만든다. 문서 화소 합 한도 안에서만 늘어난다.
- (11-28 해결) 잡음 있는 스캔은 쪽 그림 PNG 재인코딩이 시간의 절반 가까이를 썼다(MuPDF 인코더, 한 줄로 돌고 GIL을 쥠).
  OCR 입력 PNG를 OpenCV로 인코딩하도록 바꿨다(`preprocess.encode_png`): 화소는 같고(무손실, 말뭉치 전체 대조) 한 쪽
  1.1초 → 0.12초다. 압축 단계가 낮아 쪽 PNG는 커진다(잡음 쪽 4.3 → 6.3MB).
- (11-28 해결) 판독이 이벤트 루프에서 돌던 구조는 전용 작업 스레드 + 프로세스별 동시 1건으로 바꿨다(`ocr-execution.md`).
  판독 스레드가 GIL을 쥔 C 호출 동안의 짧은 지연은 남는다.
- 전북AI 계층(`JbaiOcr`, 기본 꺼짐)도 `preprocess` 한도를 먼저 지나므로 한도 초과 문서는 외부로 보내지 않는다. 한도 안
  문서의 200dpi 전송용 JPEG는 지금도 모든 쪽을 한꺼번에 만든다(쪽 수·화소 한도 안에서만).
- 한도 값은 합성 문서 기준이다. 실제 서식 분포는 Phase 2 표본과 함께 다시 본다.
- (11-28 정리) youth의 화질 정책은 원본 해상도 점수가 0.6 미만이면 판독 여부와 무관하게 `LOW_IMAGE_QUALITY` FAIL이다.
  이 점수는 파일의 원본 그림에서만 재므로 한도로 읽지 않은 문서라도 그림이 실제로 미달이면 FAIL이 유지된다(파일 사실).
  반대로 쪽 상자만 큰 문서(A2·A1 쪽, 72dpi 변환 PDF)가 미달로 계산되던 것은 근거 없는 FAIL이라 측정을 고쳤다
  (`failure-filtering.md` 11절 page-box rule). 담당자 화면의 사유 `detail`에 측정 근거와 '읽지 않은 문서'임을 남긴다.
- 글자층 PDF의 종류 미판별 대체 판독(`TEXT_RECLASS_*`)이 한도를 넘으면 글자층은 이미 다 읽었어도 `RESOURCE_LIMIT`
  확인필요로 표시된다(그림 길 대체 판독과 달리 '읽지 않음'으로 남는다). 판정은 확인필요로 같다.
